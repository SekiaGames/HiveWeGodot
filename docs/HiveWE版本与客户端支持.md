# HiveWE 版本与客户端支持

上游从未支持 1.27。每个版本锁定一段客户端版本，数据从那个版本的客户端里读。地图格式的读取另说，解析层保留了对老格式的分支。

本工程固定在上游 commit `cd6d61a`（2026-10-11），比 0.10 正式版晚五个月。

## 1. 客户端版本

| HiveWE | 发布 | 对应客户端 | 说明 |
|---|---|---|---|
| 0.1 | 2019 前后 | 未标注 | 只画地形、放装饰物、涂路径图 |
| 0.2 | — | 未标注 | 实例化渲染，单位渲染，基础动画 |
| 0.3 | — | **1.29** | 层级里去掉 `war3Patch.mpq`，换成 `deprecated.mpq`（1.29） |
| 0.4 | — | **1.30** | BLP1、高度图导入、地图信息编辑、Ribbon 工具栏 |
| 0.5 | — | 1.30 延续 | 小地图、完整撤销重做、JASS 编辑器 |
| 0.6 | — | **1.31** | 地图脚本生成、JASS 高亮与补全、触发器标签页 |
| 0.7 | 2025-09 | **Reforged** | 加 Reforged 支持、Lua、对象编辑器、单位调色板 |
| 0.8 | 2025-10-20 | Reforged | 触发器编辑器恢复、路径图导入导出 |
| 0.9 | 2025-12-14 | Reforged | 全局搜索、Ability Insights、队伍颜色 |
| 0.10 | 2026-05-18 | **2.0.3+** | 游戏常量编辑器、资源管理器、地图缩放、坡道与水编辑 |

论坛上作者与社区的口径更直接：

> The current version of HiveWE (0.9) only works on Reforged. The previous build (0.6) only works on Warcraft 3 1.31. None of HiveWE builds are intended for older versions of Warcraft. 1.31 is bare minimum.

0.10 的下载页运行要求写的是 64 位 Windows、OpenGL 4.5、VC++ 2022 运行库、**Warcraft 2.0.3 或更高**。

想要 1.26 / 1.27 的三方编辑器，社区推荐 JNGP 或 WEX。

## 2. 数据来源的两次切换

| 阶段 | 游戏数据来源 |
|---|---|
| 0.1 ~ 0.2 | 直接读客户端目录下的 `*.mpq` |
| 0.3 ~ 0.6 | MPQ 加 `deprecated.mpq`，1.29/1.30/1.31 各自的布局 |
| 0.7 起 | 改为 CASC（`war3.w3mod:_hd.w3mod:` 之类的路径），MPQ 退役 |

当前代码里 `Hierarchy` 只有 `open_casc()`，没有 `open_mpq()`。但 `open_file` 的查找链里仍然保留着 `overrides → imports → local_files → casc` 四段，`local_files` 这一段是纯文件系统读，不关心数据来自 MPQ 还是解包目录。

本工程就是接在这一段上：用自己的 MPQ 后端顶掉 CASC，同时让 `testdata/warcraft` 走 `local_files`。

## 4. 相对官方 WE 缺的

0.10 口径，官方 World Editor 有而 HiveWE 没有或很弱的：

| 能力 | 状态 |
|---|---|
| 场景信息里的 Forces / Techtree / Abilities / Upgrades | 界面在，功能未实现 |
| 战役（Campaign）编辑 | 没有 |
| 地形高度图导出 | 只有导入 |
| 自定义 UI（FDF 框架） | 没有 |
| vJASS 编译 | 靠外部，原生只有 JASS / Lua |
| 触发器 GUI 编辑 | 0.8 恢复，参数编辑弱于官方 |
| 多人协作、版本控制集成 | 没有 |
| 布局保存 | 没有 |
| 模型编辑器 | 预览为主 |

反过来，HiveWE 有而 WE 没有的：1000+ 格笔刷、直接改水体高度、全局 tile pathing、路径图直接画、双击 Shift 全局搜索、大地图加载快一个数量级。

## 5. 附：注入式编辑器（JNGP / WEX / YDWE）

这一类是 1.26 / 1.27 / 1.28 时代的三方方案。它们都不做独立编辑器，而是往暴雪原版 `worldedit.exe` 里注入补丁，把原版编辑器增强。原版闭源，所以它们能改什么，取决于逆向出多少东西。

### 5.1 JNGP（Jass NewGen Pack）

2008 年前后由社区多人接力，核心是 Grimoire，一个内存补丁框架。因为 Grimoire 从 1.21 起就没再更新，JNGP 必须捆绑 1.21 版的 `worldedit.exe` 一起发布，所以它实际是用旧编辑器打开新版本的地图。

组件：

| 组件 | 作用 |
|---|---|
| Grimoire 1.5 | 注入框架，其余插件都挂在它上面 |
| UMSWE 5.0 | 解除 WE 的各种限制（装饰物数量、地形高度等） |
| JassHelper | vJASS 编译器，替换掉 WE 内置的 JASS 编译器，有 Vexorian 和 Cohadar 两个分支 |
| AdicHelper | cJASS 预处理器 |
| TESH | 触发器编辑器里的语法高亮 |
| pJass | 语法检查，报告行号与错误 |
| Grimex | 扩展库，`ObjectMerger` 之类，能在脚本里批量生成对象 |
| Colorizer | 自定义代码配色 |
| Campaign Builder | 战役打包 |

支持到 1.27b（JNGP 2.0）。1.28 起 Grimoire 的硬编码地址对不上，直接失效。

用久了暴露的问题：GUI 的 Hashtable 函数会崩编辑器、MPQ 结构变化后要手动导入 CD-Key、新版 WE 的 Validate 功能完全没有。Hive 上这个资源现在挂着「obsolete，都去用 WEX」的评价。

### 5.2 WEX（SharpCraft World Editor Extended）

MindWorX 从 2016 年底开始做，基于他自己的 SharpCraft（.NET 注入框架），定位是 JNGP 的接班人。跑起来需要 .NET 4.6.1 和 VC++ 2012 x86 运行库。

和 JNGP 最大的结构差异是插件系统：每个功能是独立插件，靠依赖注入挂载，一个插件出问题不影响其它插件。更新到新版本时通常只改一个文本文件里的地址表。

组件：

| 功能 | 作用 |
|---|---|
| JassHelper | vJASS 编译器，完全替换内置编译器 |
| TESH | 触发器编辑器语法高亮 |
| Grimex | ObjectMerger 等扩展 |
| 解限 | 装饰物、可破坏物数量；地形高度范围；陡崖 |
| Object ID 对话框 | 新建对象时手动指定四字 ID |
| 地图尺寸 | 可玩区域扩到 480×480（原版上限 256×256） |
| WurstScript | 实验性支持 |

支持版本（Bundle v0.1.0.2，2018）：

| 客户端 | 状态 |
|---|---|
| 1.26.0 | 完全支持 |
| 1.27.0 / 1.27.1 | 完全支持 |
| 1.28.0 ~ 1.28.5 | 完全支持（1.28.3 跳过） |
| 1.29 | 实验性（v0.1.3.1） |
| Reforged | 不支持 |

2018 年 4 月之后没再更新，Reforged 改动过大，社区也停了。

### 5.3 对照

| | JNGP | WEX |
|---|---|---|
| 注入框架 | Grimoire（C，2008） | SharpCraft（.NET） |
| 捆绑旧编辑器 | 是，绑定 1.21 的 worldedit.exe | 否，直接注入当前版本 |
| 插件隔离 | 无，一个崩全崩 | 有，插件独立 |
| 支持到 | 1.27b | 1.28.5（1.29 实验） |
| vJASS | 有 | 有 |
| 语法高亮 | TESH | TESH |
| 解限 | UMSWE | 内置 |
| 最后更新 | 2012 前后 | 2018-04 |

### 5.4 中文社区的 YDWE

YDWE（Yet another Development World Editor，仓库 `actboy168/YDWE`，3000 多次提交）在国内用得很广。架构上它和上面两款是同一类：

`YDWEStartup` 干的第一件事是**把一份定制的 WorldEdit 可执行文件复制进游戏目录**，再用 `ydbase` 注入。`ydbase` 里明写着 IAT/EAT hook、inline hook（2018 年后换 detours）、DLL 注入。其它模块挂在上面：

| 模块 | 作用 |
|---|---|
| `yd_lua_engine` | Lua 引擎注入游戏进程，地图逻辑用 Lua 写、能打断点 |
| `yd_virtual_mpq` | 运行时挂载覆盖文件，改图不用改原包 |
| `yd_jass_api` / `yd_jass_debug` | JASS 扩展与调试 |
| JassHelper / pjass / cjass / TESH | 与 JNGP 同源的脚本工具链 |
| w3x2lni | 地图转 INI 结构，可读可写 |

支持 1.20 ~ 1.27 这一段。后来的 `YDWE PK` 走另一条路，目标是让重制版地图能用，但前提是那张图没被重制版编辑器存过。

### 5.5 开源的边界

这三款都开源，但能看到的东西是有限的：

| 能拿到 | 拿不到 |
|---|---|
| 注入框架、hook 库、插件系统 | 地形算法 |
| Lua 引擎、脚本工具链 | 地图文件的读写实现 |
| 逆向出来的地址表和结构体偏移 | 编辑器界面逻辑 |
| 配置界面、打包脚本 | 渲染 |

原版 `worldedit.exe` 闭源，所以它们对编辑器的"理解"全是逆向结论：某个函数在第几个地址、某个对象的成员在第几个字节。游戏一打补丁，这些数字全废，只能重新找。

这就是三款工具都绑死版本区间的根本原因，也是 JNGP 必须捆 1.21 编辑器、YDWE 必须自带定制 WorldEdit 的原因：它们改的那份二进制是固定的一份。

### 5.6 与本工程的关系

这几款和 HiveWE 是两条路线：它们增强原版编辑器，界面、渲染、数据读写全是暴雪的；HiveWE 自己重写了渲染和界面，只复用地图格式的读写逻辑。

我们要的是一套能接到 Godot 上的 C++ 数据层，JNGP 和 WEX 没有这个东西，它们的逻辑都在注入补丁里，跟 `worldedit.exe` 的二进制地址绑死。

它们的意义在别处：如果客户需要在 1.27 上改图、又不接受 HiveWE 的操作习惯，这两个是现成的、成熟的方案，不必自己造。

## 6. 对本工程的影响

**版本差异在数据层很浅。** 我们要移植的是地形数据、笔刷、撤销、地图读写，这些从 0.2 起就有，0.3 补上调色板和全局 pathing，之后基本没动过结构。0.7 之后新增的是对象编辑器、单位调色板、Lua 这类，属于 UI 层的工作量，跟数据层解耦。

**客户端版本对我们不构成约束。** 上游要求 1.31 或 Reforged，是因为它要从那个客户端里读数据。我们把数据源换掉了（MPQ 后端 + `testdata/warcraft`），客户端要求自然失效。1.27 的 MPQ 能读，是因为 `local_files` 那条分支本来就跟数据来源无关。

**地图格式兼容是解析层的事，跟版本无关。** 上游保留了 `pre-1.31 trigger` 分支、`war3map.doo` 的 v7/v8/v13 分支、`war3map.w3i` 的 v18/v25/v31 分支，这些都是为了读老地图，而不是为了跑在老客户端上。我们实测的三张 1.27 地图全部走通了这些分支。

**结论：不需要换版本。** 固定 `cd6d61a` 就行。如果要往对象编辑器、触发器编辑器推进，这个 commit 已经包含 0.7 之后的全部能力，比 0.10 正式版还新。真遇到 1.27 特有的数据差异（比如 `ItemMetaData.slk` 缺失），按现有方式在补丁表里加容错，比切换版本成本低。
